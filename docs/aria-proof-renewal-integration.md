# Root integration decision: authorization identity versus proof freshness

The first source proof handoff and durable foundation are connected conceptually but need one additional seam before real consumers. Source capabilities/leases expire after60seconds and are per-query; `putGrant` deliberately increments local authorization version and invalidates jobs/profile. Calling putGrant for every legitimate proof refresh would destroy resumability and invalidate unchanged knowledge. Do not solve this by making stale proof valid forever or by comparing account strings alone.

Source owner adds an opaque random `authorization` identity, stable for the same caller plus exact current source authorization state within the process incarnation, across short-lived capability/lease renewal. Generate UUIDs; do not derive credential hashes. When current auth data generation/publication/recording/account state differs, mint a different identity. Process restart changes incarnation and identities. Include this identity in source_capabilities and each validated receipt; old capability validation remains strict and TTL unchanged. This identifies the observed authorization generation, not a self-verifying timeless receipt or data snapshot.

DB owner adds transactional proof-freshness renewal for an existing enabled grant only: exact id+expected local version+same captured source authorization identity, new verified expiry, and nonblocking SourceProofValidator acceptance of the proposed receipt-backed grant. Update freshness only; do not advance local permission version/learning epoch or invalidate existing jobs/evidence/profile. Changed source identity/scope/account still uses putGrant/revoke and invalidates as before. A source-consumer verified cache maps receipt incarnation+authorization and exact allowed scope to the local grant, checks monotonic receipt age, and refreshes before commit/retrieval. Missing/unreachable/expired proof still rejects.

Required regressions: same-source authorization legitimate capability renewal after expiry preserves local job vector/profile and permits resume with a fresh verified proof; stale/missing/unverified receipt cannot renew; changed authorization or version rejects renewal; real source state change/process incarnation changes opaque identity even for same account and invalidates old handles. Fresh source reads remain tied to their exact lease/query. This is an integration extension within the newly authorized phase, not an old-phase review-counter reset or runtime acceptance.
