Root inspection established these production seams:

- Fluidify `FluidifyToolHost` already captures `HistoryAccess(account,generation)` plus web token generation and fences result/fragments. History generation changes on logout, recording changes and deletion; source process recreation resets in-memory counters. Use a process incarnation identity too, so a same-number generation after restart is not accepted as an old proof.
- CV `AuthRepository.dataEpoch()` is distinct from authenticationEpoch. The original data epoch must fence password-to-CIE alias/method changes even when authenticationEpoch is preserved. Expose exact current source account/student and ready state through the signed source tool; never mutate globally selected year to serve scoped reads.
- Transport agreement must be typed v2. A source-specific versioned proof capability must be explicitly advertised by the source and checked by the client; presence of legacy text alone is insufficient. Preserve no-negotiation protocol1 and signature/confirmation gates. It is acceptable to expose additive `source_lease`/validation tools with an explicit versioned contract using the existing typed transport; do not raise global protocol unilaterally.

Define and document actual interoperable tool/data API before consumers. Capture caller identity, domain/authority, account/student and explicit normalized source scope, source process incarnation, data authorization generation and short validity. Return an opaque generation token/proof, never tokens, passwords or secret credential material. Expected account/scope/proof inputs must MATCH current state; a model argument may not choose another account. Old proof after source process death/logout/login/recording revocation/account change must fail, including same-account reconnect. No automatic source switch. Read+post-read validation must guard returned evidence; application local revoke/forget checks remain atomic at commit/retrieval. External proof is a point-in-time check: do not claim a distributed atomic guarantee across processes; bound proof freshness and revalidate before consumption/prompt, invalidate on observed change and fail closed offline/unsupported.
