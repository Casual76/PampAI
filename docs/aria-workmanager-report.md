# Connected silent worker implementation

ROOT explicitly transferred app/core/feature writes and the sole compiler runner after the UI author's release. The connected implementation and final validation are complete. Sources and runner are released to ROOT for integrated visual inspection and two independent reviews; this report is not self-approval or live runtime acceptance.

The app now starts `ResearchScheduler` after Hilt injection in its existing owned application scope. `Configuration.Provider` supplies `ResearchWorkerFactory`, which retains a lazy provider of the scheduler; the Android queue obtains WorkManager only inside scheduling operations. The merged manifest removes only the default WorkManager initializer and retains the application and other startup components. No AssistantRuntime dependency enters this graph. Actual app Hilt compilation/assembly passed; synthetic on-demand Application configuration and custom factory construction/execution are tested.

Core adds ordinary `work-runtime-ktx:2.12.0` and matching test helpers. No feature dependency change or new Hilt WorkManager plugin was needed. There is no expedited/foreground promotion, notification, speech, permission request, UI launch or conversational submission in the scheduler/worker paths. Existing reminder, foreground conversation service, voice, overlay and startup catalog behavior remain separate.

Each enabled, explicitly configured area gets a unique periodic safety wake at its saved cadence (minimum 15 minutes), plus one-time continuation slots. The safety wake repairs interrupted metadata/enqueue transitions; persisted next eligibility governs actual execution. Per-area requests carry UNMETERED versus CONNECTED and battery-not-low constraints from saved settings. Periodic UPDATE preserves in-flight work; continuations have distinct persisted deterministic slot IDs and KEEP. Ordinary completion does not replace/cancel its current unique request. Android timing remains best effort.

`ResearchScheduleStore` persists generation, current BACKGROUND job pointer, slot/work ID, operation count, reason, state, last attempt/success and next eligibility in a separate DataStore. Room schema 7 is unchanged. WorkManager operation completion establishes enqueue status; execution records RUNNING; only a completed durable cycle advances success. Startup reconciles interrupted RUNNING markers and terminal/missing WorkRequests against actual WorkInfo before allocating a repair slot. Profile UI consumes domain status, without WorkInfo, raw IDs, JSON or secrets.

`ResearchScheduler.reconcile()` is callable and also observes local settings/plans/caps/grants/exclusions during app lifetime. UI area save/disable and cap save explicitly call it. Missing/disabled/incomplete/invalid setup, absent model/read consent, missing exact model authorization, revoked scopes, unusable windows or monetary caps without trusted tariffs suspend/cancel without autonomous acquisition. Connecting/discovering an app never enables background work. Default setup is off, and disabled startup tests perform zero enqueue/admission/acquisition.

`DurableFoundation.backgroundJob` finds unfinished BACKGROUND work even if future-due or claimed. Background creation atomically adopts an existing current-epoch job before inserting another, so death between Room admission and DataStore pointer persistence cannot create a second job. Worker resumes this job and its checkpoints; live claims defer until their lease deadline. Foreground/temporary jobs are excluded from adoption/eligibility. Existing reader admission signatures/behavior are preserved: budget execution preflight belongs to the scheduler, while the reader remains separately fenced and the ledger remains authoritative before each model wire.

Every invocation runs at most one background tranche under a 150-second tranche deadline. Existing per-step/page/record bounds remain, with a finite 16,384-progress ceiling per cycle. Progress schedules the next slot, completion schedules no earlier than success plus cadence, and known cooldown eligibility schedules future work without sleeping/retrying inside the worker. Exhausted budgets can yield only to an already persisted usable future window; no window, quota, tariff, provider reset or recurring replenishment is manufactured.

`BackgroundResearchGuard` is installed only by background runner entry points. ResearchSources checks it immediately before discovery/catalog negotiation and every source capability/lease/validate/read wire. It checks foreground priority and current setup/plan/job fences; existing ledger admission independently checks priority and exact model/bounds before model dispatch. This cannot stop a request already dispatched remotely. Runtime coordinator startup recovery removes only confirmed older-process priority markers through its explicit API, excluding all live same-process IDs; reservations remain untouched. The application manifest uses the default single process.

Cancellation before model dispatch can schedule safe continuation after a local delay/claim expiry while retaining its checkpoint. Possible model use without a completed synthesis checkpoint remains reserved and suspends automatic repetition. Process-death adoption applies the same conservative check. Completed synthesis steps can be finalized without another model call. Storage errors and unavailable/invalid sources produce persisted suspension where storage is available, never an uncapped/provider-substituted retry.

Profile updates now display observed queued/running/suspended status, last attempt, last completed update and earliest next eligibility. Setup/enqueue are not presented as success. The existing Fluid surfaces, navigation and exact model picker are preserved. Two new synthetic screenshot cases exercise the actual extracted production area row in light/dark themes; both were individually inspected for wrapping, readable status/timestamps and unknown completion/eligibility.
